# 권한 체계 도입 계획 (외부 로그인 · 관리자·재정담당·열람자, PC앱 전용)

> 상태: **계획만, 미착수**(2026-11-24). 기존 `관리자-로그인-계획.md`(로컬 비밀번호 방식)를 대체한다.
> DB 구조가 바뀌므로 4단계 착수 전에 다시 승인받는다. 브라우저(시연용)는 지금 그대로: 로그인·암호화·역할 없음.

## 1. 배경과 결정
- 외부 로그인(Google)으로 사용자를 확인하고, 세 역할로 할 수 있는 일을 나눈다. 역할은 계정마다 하나.
- 로컬 비밀번호·복구 키·보안 질문·3회 차단은 쓰지 않는다(로그인 서비스가 맡음).
- 데이터 열쇠는 Windows 계정 단위(DPAPI, `safeStorage`)로 잠근다.
- **앱을 실행할 때마다 Google 로그인**한다(인터넷 필요). 로그인한 뒤 실행 중에는 인터넷이 끊겨도 쓸 수 있다. 세션·토큰은 저장하지 않는다.
- 사용자 결정: 열람자는 종합보고서 탭만(인쇄·PDF 가능) / 관리자 탭은 관리자만 / 자동 잠금 15분 + 해제용 PIN.

- 메뉴: 열람자는 보고서(종합보고서 탭만)·설명서·설정(**화면 테마 항목만**)을 본다. 재정담당은 관리자 탭만 빼고 본다.
- 연도 잠금은 잠그기만 재정담당도 가능하고, **풀기는 관리자 전용**(재정담당이 마감한 연도를 혼자 다시 열어 고치는 것을 막음).
- 복원·전체 초기화는 관리자 전용(복원으로 일괄 삭제 제한·연도 잠금이 우회되는 것을 막음).
- 연도 잠그기는 재정담당도 쓰므로 관리자 탭이 아닌 헌금 입력/보고서 쪽 화면에 둔다(위치는 7단계에서 확정). 풀기 단추는 관리자에게만 보인다.
- **한계:** 데이터는 렌더러의 IndexedDB에 있고 열쇠도 렌더러가 갖는다. main이 실제로 막을 수 있는 것은 계정·역할 관리, 토큰, 사용자 목록 파일뿐이다. 그 밖의 역할 제한(헌금 쓰기·복원·초기화 등)은 **화면 규칙**이며, 데이터 파일을 직접 여는 사람은 막지 못한다.

## 3. 외부 로그인 흐름 (Electron main, OAuth 2.0 + PKCE)
1. 시스템 기본 브라우저로 로그인 페이지를 연다(내장 창 사용 안 함). 열기 전에 URL 호스트를 검사한다.
2. 결과는 **loopback(127.0.0.1, 무작위 포트)** 로 받는다. `state`·`nonce` 확인, 한 번 받으면 서버를 닫고 시간 제한을 둔다.
3. ID 토큰 검사: `iss`, `aud`, `exp`, `nonce`, 서명(JWKS), `email_verified = true`. 서명 검증은 Node 내장 `crypto`(JWK)로 가능한지 먼저 본다(새 의존성 지양).
4. 계정 식별은 이메일이 아니라 `sub`.
5. 토큰은 저장하지 않는다(로그인 확인에만 쓰고 메모리에서 버림, 리프레시 토큰도 요청하지 않음). 화면에는 토큰을 넘기지 않는다.
- **context7 확인(2026-11-24, Google 공식 문서):** 데스크톱 앱 클라이언트를 만들며, 데스크톱 앱은 공개 클라이언트라 비밀을 지킬 수 없으므로 **항상 PKCE**를 쓴다. 리다이렉트는 `http://127.0.0.1:포트`(무작위 포트) 방식이 지원된다. client_secret은 발급되지만 비밀로 취급되지 않는다 → 토큰 교환에 필요하면 앱에 넣어도 되는 값으로 본다(필요 여부는 구현 때 실제 호출로 확인).
- 출시 상태는 **공개(production)** 로 확정. 참고: 요청 범위가 `openid email profile`뿐이면 "테스트" 상태에서도 리프레시 토큰이 7일 만에 만료되지 않고 누구나 쓸 수 있다. 다만 테스트 상태는 경고 화면이 뜬다. 이 앱은 토큰을 저장하지 않으므로 만료와 무관하다.

## 4. 계정·역할 저장
- 위치: `%APPDATA%\StewardLedger` 설정 파일(IndexedDB 밖). 백업에 넣지 않는다.
- 항목: `{ sub, email, role, addedAt, disabled }`, 최대 10명.
- 등록: 관리자가 **이메일로 미리 등록** → 첫 로그인 때 `email_verified`를 확인하고 `sub`를 묶는다. **목록에 없는 사람의 로그인은 거절**한다.
- 목록이 비었을 때 처음 로그인한 사람이 관리자가 된다(이 PC의 첫 사용자라는 전제).
- 관리자는 1~2명.
  - 1명이면 추가만 가능(강등·사용 중지 거절). 2명이면 한 명을 내릴 수 있다. 교체는 "추가 → 기존 관리자 내리기".
  - 관리자 자신은 사용 중지할 수 없다.
- 사용 중지는 이 PC의 파일이라 로그인 직후 바로 확인한다(실행할 때마다 로그인하므로 지연 없음).
- **관리자를 잃었을 때:** PC 소유자가 목록 파일을 지우고 처음 로그인자를 새 관리자로 등록. 데이터는 DPAPI 열쇠로 그대로 남는다. 즉 역할은 PC 소유자에 대한 보안 경계가 아니다.
- 같은 Windows 계정이면 목록 파일을 고쳐 관리자가 될 수도 있다(위와 같은 한계).

## 5. 데이터 보호와 백업
- 데이터 열쇠: 무작위 256비트, 처음 실행 때 생성, `safeStorage`(DPAPI)로 잠금. 같은 PC·같은 Windows 계정에서만 풀린다. **구현은 `electron/pcKey.cjs`의 `createPcKeyStore` 방식을 따르되 별도 파일(`data-key.bin`)** 로 둔다. 동기 safeStorage는 Electron 46에서 삭제되므로 비동기 함수(`encryptStringAsync` 등)만 쓴다.
- **백업 키와 다른 점:** `pcKey.cjs`는 키 파일을 풀 수 없으면 `.old`로 치우고 새 키를 만든다(백업은 새로 만들면 되므로). 데이터 열쇠는 **자동으로 새로 만들면 안 된다**(데이터를 영구히 못 열게 됨). 풀 수 없으면 "수동 백업으로 복원하세요" 안내만 하고, 저장소에 데이터가 하나도 없을 때만 새로 만든다.
- Windows `safeStorage`(DPAPI)는 같은 PC의 **다른 사용자**는 막지만 **같은 사용자 권한의 다른 프로그램**은 막지 못한다(Electron 문서).
- 건별 암호화(금액·이름·메모). 날짜·사람 id 등 색인용 칸은 평문. 칸 구분·성능 시험은 `관리자-로그인-계획.md` 5장을 따른다. 암호화·풀기는 저장소 층(`storageService.ts`)에서만.
- 수동 백업: 백업 암호(기존 규칙, PBKDF2 60만 회). DPAPI에 묶지 않아 다른 PC에서 암호만 알면 복원, 복원 뒤 그 PC의 DPAPI로 다시 잠근다. 계정 목록은 백업에 없다 → 새 PC에서는 처음 로그인자가 관리자.
- 자동 백업(PC 키): 같은 PC·같은 Windows 계정에서만 복원.
- **위험:** Windows 계정 비밀번호 초기화, 프로필 손상, Windows 재설치 시 DPAPI 열쇠를 잃고 **자동 백업도 함께 못 푼다.** 이때 복구 수단은 수동 백업뿐 → `BackupReminderBanner`·첫 실행 화면·설명서에서 수동 백업 보관을 강하게 안내.
- 이력(`audits`)에 `actor`(sub 또는 가린 이메일)를 추가한다. **4단계 DB 구조 변경과 같은 승인·같은 마이그레이션**으로 한 번에. 로그인 실패·역할 변경도 기록한다.

## 6. 자동 잠금과 PIN
- 입력·클릭·휠이 **15분** 없으면 전체 화면 잠금(입력 중인 내용은 유지). 값은 한 곳의 상수, 시험 때만 `STEWARD_TEST_IDLE_MS`로 단축(포장본에서는 무시).
- 해제는 **PIN**(숫자 6자리). 로그인 후 처음 한 번 만든다. 계정(`sub`)에 묶어 scrypt 해시+솔트만 목록 파일에 저장, 백업에는 넣지 않는다. 데이터 열쇠와는 무관.
- PIN 5회 연속 실패 → Google 재로그인 요구(오프라인이면 온라인이 될 때까지 잠김). 재로그인 후 PIN을 다시 만든다. 잊었을 때도 재로그인.
- 앱을 켤 때는 매번 Google 로그인(PIN이 아님). 로그인 직후 PIN이 없으면 만든다. PIN은 실행 중 자동 잠금 해제에만 쓴다.
- IPC: `auth:set-pin`, `auth:verify-pin`.
- 한계: PIN은 자리를 비운 사이 화면을 보는 사람을 막는 용도이며, 같은 Windows 계정으로 파일을 직접 여는 사람은 막지 못한다. 설명서에 밝힌다.

- [ ] 0. 기존 계획 `관리자-로그인-계획.md`에 "대체됨" 표시(승인 후)
- [x] 1. 인증 코어 `electron/auth.cjs`: OAuth/PKCE, 토큰 검증(저장 없음), IPC, 데이터 열쇠 DPAPI 잠금 (2026-11-24 구현. 요청 범위는 `openid email`로 줄임(이름·사진 불필요). 데이터 열쇠 저장소 `dataKey.cjs`는 만들어 시험까지 했고 main 연결·화면 전달은 4단계. 로그인 클라이언트 ID는 gitignore된 `electron/authConfig.local.cjs`에 넣어야 실제 로그인이 됨 — 처음엔 `authConfig.cjs`에 직접 넣고 `skip-worktree`로 숨겼으나 브랜치 전환이 막혀 분리)
- [x] 2. 로그인 화면 `src/components/auth/`, `AuthGate`가 `AppProviders`를 감싼다(`desktop()`일 때만; 브라우저 모드 그대로) (2026-11-24 구현. [취소]·인터넷 끊김 안내 추가. 저장소 열기(`openStorage`)는 아직 로그인 앞이며 4단계에서 로그인 뒤로 옮긴다)
- [x] 3. 계정·역할 저장·처음 관리자·PIN, `src/services/auth/roles.ts`의 `can(role, action)`(탭 단위 `report:summary|list|personal|audit`, `admin` 포함) + 표 기반 테스트 (2026-11-24 구현. `electron/userStore.cjs`는 규칙·PIN까지 시험 완료, 로그인 때 `admit`으로 연결됨. **계정 관리 IPC(등록·역할 변경·사용 중지)는 아직 노출하지 않음 → 5단계에서 관리자 가드와 함께, 화면은 6단계.** 역할을 화면 전체에 전달하는 컨텍스트도 5단계. main은 `can` 표를 쓰지 않고 계정 관리만 `role === 'admin'`으로 막는다(헌금·복원 등은 화면 규칙이라 main에서 막을 수 없음))
- [x] 4. 건별 암호화 + 처음 암호화 이전 + 이력 `actor` (**DB 구조 변경, 2026-11-24 승인·구현**). 구현에서 정한 것:
  - 읽기·쓰기는 `storageService.ts` 한 곳에서만 잠그고 푼다. IndexedDB 트랜잭션 안에서 비동기 WebCrypto를 기다리면 트랜잭션이 먼저 끝나므로 `Dexie.waitFor`로 감쌌다(Dexie 공식 문서가 WebCrypto 용도로 안내). Dexie 스키마(버전)는 바꾸지 않았다: 색인 칸은 그대로고 행에 `enc`만 늘었다.
  - 암호문은 행 id를 `additionalData`로 묶어(`d:<id>`·`a:<id>`·`members`) 다른 행의 암호문을 옮겨 붙이면 풀리지 않는다. `enc`가 없는 평문 행도 그대로 읽혀 이전 도중·브라우저 모드가 동작한다.
  - `audits.actor`(고친 사람 이메일)는 암호화되는 칸에 넣었다. 로그인이 없는 브라우저 모드에서는 기록하지 않는다. **화면에 표시하는 것(수정·삭제 이력 탭)은 아직 안 함.**
  - 로그인 직후 `prepareData`: 열쇠 받기 → (이전이 필요하면) 이 PC 키로 자동 백업 → 달·해 단위 트랜잭션으로 암호화(이어하기 가능) → 표식 `meta_encrypted`. 백업이 실패하면 암호화하지 않고 [다시 시도].
  - 열쇠를 풀 수 없을 때: 저장소가 비어 있으면 새 열쇠를 자동으로 만들고, 데이터가 있으면 안내 화면에서 사용자가 두 번 확인해야만 모두 지우고 새로 시작한다(`.old` 열쇠 파일은 남김).
  - 앱이 열리기 전(로그인·준비 중)에 창을 닫으면 '백업 생략'으로 답해 종료가 멈추지 않는다.
  - 성능: Node WebCrypto로 26만 건 암호화 4.0초·복호화 3.3초(건당 암호화 칸 3개 JSON). 앞선 Electron 시험(읽기+풀기 4.0초)과 비슷한 수준이며, 연 6.7만 건 규모면 첫 진입이 약 1초 안팎 늘어난다고 본다. **실제 Electron 화면의 시연 데이터 20만 건 측정은 아직 안 했다(수동 확인 항목).**
  - 한계: `storageService`의 읽기를 거치지 않고 `db`를 직접 읽는 코드가 없는지는 확인했다(시험 코드만 직접 접근). 열쇠는 화면 프로세스 메모리에서 `extractable: false`로만 보관된다. 로그아웃·잠금 때 열쇠를 버리는 동작(`setDataKey(null)`)은 6단계 자동 잠금에서 연결한다.
- [x] 5. 역할 적용: 메뉴·보고서 탭 숨김, **페이지 키로 직접 여는 경로도 차단**, main IPC 차단(계정·역할 관리) (2026-11-24 구현). 구현에서 정한 것:
  - 역할 판단은 `src/services/auth/access.ts` 한 곳(`allowed`·`assertAllowed`). 로그인이 없는 브라우저(시연) 모드는 제한 없이 관리자와 같고, PC앱에서 로그인 전(역할 없음)은 모두 거절한다. 역할은 로그인 때 정해져 실행 중 바뀌지 않으므로 화면이 그때그때 읽는다(로그아웃·잠금은 6단계).
