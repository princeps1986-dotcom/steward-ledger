# 관리자 로그인 · 관리자 탭 · 저장 데이터 암호화 계획 (PC앱 전용)

> 상태: **대체됨**(2026-11-24) → `권한-체계-계획.md`(외부 로그인·역할 방식). 5장(저장 데이터 암호화)의 칸 구분·성능 시험만 새 계획이 참조한다. 아래 본문은 보존용.
> (이전 상태: 계획만, 미착수(2026-11-23 정리). 데이터베이스 구조가 바뀌므로 착수 전에 다시 승인받는다.)
> 브라우저(시연용)는 지금 그대로 둔다: 로그인 없음, 암호화 없음, 전체 초기화는 설정 정보에 그대로.

## 1. 목적과 결정 사항

- PC앱에 관리자 로그인을 두고, 로그인한 관리자 비밀번호로만 헌금·성도 데이터를 풀 수 있게 한다.
  데이터 폴더(`%APPDATA%\StewardLedger`)를 복사해 가도 이름·금액·메모를 읽을 수 없게 하는 것이 목표.
- 사용자 결정
  - 복구 수단: **일회용 복구 키 + 보안 질문/답변 둘 다**
  - 3회 초과 실패로 종료된 뒤 다시 실행하면 **10분** 로그인 차단
  - 헌금 일괄 삭제: **사유 입력 + 건별 수정·삭제 이력**
  - 저장 데이터 암호화: **건별 암호화**, 데이터 열쇠는 **관리자 비밀번호로 보호**(로그인과 함께 구현)

## 2. 계정과 열쇠 (main 프로세스)

### 2.1 계정 파일 `%APPDATA%\StewardLedger\auth.json`
- IndexedDB 밖의 별도 파일. 백업 파일에 들어가지 않는다(다른 PC로 데이터를 옮겨도 계정은 따라가지 않음 → 새 PC에서 새 관리자를 만들고 수동 백업을 복원).
- 화면은 IPC로만 확인을 요청하고, 해시·솔트·잠긴 열쇠는 화면에 넘기지 않는다.
- 쓰기는 임시 파일 → 이름 바꾸기(기존 백업 파일 쓰기와 같은 방식).

```
{
  version, idSalt,
  admins: [{ idHash, idHint, pwHash, question, answerHash, recoveryHash,
             keyByPw, keyByRecovery, keyByAnswer, createdAt }],   // 최대 3명
  lockUntil,
  failures: [{ at, idHint | null, reason }]                         // 최근 200건 = 로그인 실패 기록
}
```

### 2.2 해시
- 비밀번호·보안 답변·복구 키: `crypto.scrypt`(Node 내장, 항목별 무작위 솔트, `timingSafeEqual` 비교). 요청의 "SHA-256 등"보다 대입 공격에 강하다.
- 아이디(이메일): 소문자로 바꾼 뒤 `idSalt`로 HMAC-SHA256(찾기용으로 같은 값이 나와야 함). 화면 표시용으로 가린 이메일(`ad***@church.org`)만 `idHint`에 저장.

### 2.3 데이터 열쇠 (봉투 방식)
- 처음 관리자를 만들 때 무작위 256비트 **데이터 열쇠**를 하나 만든다. 헌금·성도 데이터는 모두 이 열쇠로 잠근다.
- 데이터 열쇠는 관리자마다 세 벌로 잠가 저장한다: 비밀번호로(`keyByPw`), 복구 키로(`keyByRecovery`), 보안 답변으로(`keyByAnswer`). 각각 scrypt로 만든 열쇠 + AES-256-GCM.
- 로그인 성공 → 데이터 열쇠를 풀어 화면의 WebCrypto 열쇠로 넘긴다(`extractable: false`로 가져와 다시 꺼낼 수 없게). 앱 잠금·종료 때 메모리에서 버린다.
- 비밀번호 변경·관리자 추가·복구 키 재발급은 데이터 열쇠를 다시 잠그기만 하면 되므로 데이터 전체를 다시 암호화하지 않는다.
- **모든 관리자의 비밀번호·복구 키·보안 답변을 잃으면 데이터는 영구히 열 수 없다.** 이때는 수동 백업(백업 암호)만이 복구 수단 → 설명서·첫 실행 화면에서 수동 백업 보관을 강하게 안내.
- 보안 답변은 복구 키보다 추측되기 쉬워, 이 경로가 전체 보안의 가장 약한 고리임을 설명서에 밝힌다.

### 2.4 IPC (`electron/main.cjs` 등록, `preload.cjs`·`src/services/desktopBridge.ts`의 `DesktopApi`에 노출)
| IPC | 하는 일 |
|---|---|
| `auth:status` | `{ stage: 'phrase' \| 'setup' \| 'login' \| 'locked', lockUntil? }` |
| `auth:phrase(text)` | `steward-ledger`와 같으면 setup 허용(관리자가 하나도 없을 때만) |
| `auth:create({ id, pw, question, answer })` | 첫 관리자는 phrase 통과 후, 추가 관리자는 로그인 상태에서만, 최대 3명. 복구 키(무작위 100비트, `XXXX-XXXX-XXXX-XXXX-XXXX`) 반환 |
| `auth:login(id, pw)` | 실패 기록. 이번 실행에서 3회 초과면 `lockUntil = 지금 + 10분` 저장 → 안내 → `app.quit()`(종료 백업 흐름 그대로) |
| `auth:recover({ recoveryKey } 또는 { idHint, answer }, newPw)` | 맞으면 데이터 열쇠를 풀어 새 비밀번호로 다시 잠그고, 복구 키는 새로 발급. 실패도 3회 규칙 |
| `auth:verify(pw)` | 자동 잠금 해제(로그인한 관리자 비밀번호만) |
| `auth:change-password(current, next)` | 현재 암호 확인 후 변경 |
| `auth:list` / `auth:failures` | 가린 아이디·생성일 / 로그인 실패 기록 |
| `auth:save-recovery(text)` | 저장 창으로 .txt 저장(`report:save-pdf`의 저장 창 방식 재사용) |

- 규칙 검사(이메일 형식, 비밀번호 규칙)는 화면과 main에서 두 번 한다.

## 3. 로그인 화면 (`src/components/auth/`)

- `src/main.tsx`: `desktop()`이 있으면 `<AuthGate>`가 `<AppProviders><App/>`를 감싼다. 로그인 전에는 앱·저장소를 그리지 않는다(데이터 열쇠가 없으면 어차피 못 읽음).
- 단계
  - **phrase:** 입력칸 바로 옆에 `steward-ledger`를 표기하고 "그대로 입력하세요" 안내.
  - **setup:** 이메일 아이디, 비밀번호·확인, 보안 질문(목록 선택)·답변 → 생성 후 **복구 키 화면**: 키 표시 + [텍스트 파일로 저장] + [인쇄], "안전한 곳에 보관했습니다" 체크 후 [계속]. 기존 평문 데이터가 있으면 이어서 **첫 암호화 이전**(5장).
  - **login:** 아이디·비밀번호, 남은 시도 횟수, [아이디/비밀번호 찾기].
  - **locked:** 남은 차단 시간 표시.
  - **찾기:** 복구 키 입력 또는 (가린 아이디 선택 + 보안 답변) → 새 비밀번호 → 새 복구 키 화면.
- 규칙 `src/services/auth/rules.ts`
  - 아이디: 이메일 형식만.
  - 비밀번호: 대문자·소문자·숫자·특수문자 각 1개 이상, 10자 이상.
  - 한글 입력 차단: 비밀번호 칸에서 조합(IME) 입력·한글 문자를 막고 "한/영 키를 눌러 영문으로 바꾸세요" 안내.

## 4. 관리자 탭 (`PageKey`에 `'admin'`, PC앱에서만 메뉴 표시)

새 `src/components/pages/admin/AdminPage.tsx` + `src/hooks/useAdminPage.ts`. 기존 `Modal`·`ConfirmFooter`·`Notice` 재사용.

- **관리자 계정:** 목록(가린 아이디), [관리자 추가](3명까지, 추가한 관리자용 복구 키 화면), [비밀번호 변경](현재 암호 확인).
- **헌금 일괄 삭제:** 단위(월/분기/연도) + 기간 → 건수·합계 미리보기 → 사유(한글 4글자 이상) → 확인창(기간·건수 다시 표시). `DonationContext`에 `deletePeriod(fromYm, toYm, reason)` 추가: 기존 `deleteDonation`의 이력 방식을 달 단위 트랜잭션으로 묶어 건별 이력 작성. 잠긴 연도는 거부.
- **연도 잠금:** 헌금이 있는 연도별 잠금/풀기. `AppSettings.lockedYears: string[]`.
  - 막는 곳: `saveBatch`·`updateDonation`·`deleteDonation`·`undoLast`·`deletePeriod`, 설정 정보의 연도별 복원(공통 `assertYearsUnlocked`).
  - 화면: 헌금 입력 날짜가 잠긴 연도면 저장 비활성+안내, 전체 입력 내역·개인별/세대별 내역의 [수정]/[삭제] 비활성 + "잠긴 연도" 표시, 수정·삭제 이력은 잠금 표시만(원래 읽기 전용).
  - 전체 복원·전체 초기화는 잠금과 무관하게 허용하되 확인창에 "잠긴 연도도 바뀝니다" 문구.
- **전체 초기화 이동:** PC앱은 설정 정보에서 숨기고 관리자 탭에 같은 확인창(10초 대기). `useSettingsPage`의 `openReset/confirmReset`을 공유 훅으로 꺼내 재사용. 브라우저는 그대로.
- **로그인 실패 기록:** 시각·가린 아이디·사유 목록.
- **5분 자동 잠금:** `src/hooks/useIdleLock.ts` — 입력·클릭·휠이 5분 없으면 전체 화면 잠금 덮개(입력 중인 내용은 유지), 로그인한 관리자 비밀번호로만 해제, 실패도 3회 규칙.

## 5. 저장 데이터 암호화 (건별)

### 5.1 칸 구분 (확정)
| 저장 위치 | 평문 | 암호화 |
|---|---|---|
| 헌금 `donations` | `date`, `id`, `memberId`, `offeringTypeId`, `familyGroupIdSnapshot`, `createdAt` | `amount`, `donorDisplayName`, `memo` |
| 이력 `audits` | `seq`, `year`, `targetId`, `action`, `timestamp` | `reason`, `beforeSnapshot`, `afterSnapshot` |
| 키-값 `kv` | `settings`, `meta_*`, `offering_types` | `members`(목록 통째로) |

- 평문 칸은 기본키·색인(날짜 범위 읽기, 성도·종류 색인, 중복 검사 `[date+memberId+offeringTypeId]`, 이력 연도 색인)에 쓰이거나 무작위 id·시각뿐이다.
- 줄 모양: 평문 칸 + `enc`(IV 12바이트 + AES-256-GCM 암호문, 내용은 암호화 칸의 JSON).
- 암호화·풀기는 저장소 층(`src/services/storage/storageService.ts`)에서만 하고, 위쪽(`DonationContext` 등)은 지금처럼 평문 객체를 다룬다.
- 푼 이름·메모 문자열은 같은 값이면 같은 문자열을 다시 쓰게(재공유) 해 메모리를 지금 수준으로 유지.
- 오류 로그(electron-log)에 이름·금액이 남지 않는지 점검.

### 5.2 백업과의 관계 (확정)
- 백업 파일(.slbk)은 지금처럼 파일 전체를 AES-256-GCM으로 잠근다. 안에는 **푼(평문) 데이터**를 넣고, 복원하는 PC가 자기 데이터 열쇠로 다시 잠근다.
- 자동 백업(종료·10분): PC 키(DPAPI) → 같은 PC·같은 Windows 계정에서만 복원.
- 수동 백업: 백업 암호 → 암호만 알면 어느 PC에서나 복원. DB 데이터 열쇠와 무관.

### 5.3 첫 암호화 이전
- 첫 관리자를 만든 직후 기존 평문 데이터를 한 번에 암호화한다.
- 순서: 이전 전 자동 백업(PC 키) → 달 단위 트랜잭션으로 줄마다 `enc`로 바꿈 → 진행 표시 → 끝나면 표식 기록. 도중에 꺼지면 다음 실행 때 남은 달부터 이어서(달마다 평문/암호화 여부로 판단).
- 저장소 버전을 올리는 구조 변경이므로 **착수 전 별도 승인**.

### 5.4 성능 시험 결과 (2026-11-23, Electron 45 화면, 한 해 26만 건, 1회 측정)
| 항목 | 평문 | 건별 암호화 | 참고: 달 단위 덩어리 |
|---|---|---|---|
| 한 해 읽기+풀기 | 1.4초 | 4.0초 (2.2 + 1.8) | 1.4 + 0.04초 |
| 26만 건 잠그기(이전·복원·시연) | – | 3.4초 | 0.1초 |
| 한 건 저장 시 추가 | – | 거의 없음 | 그 달 다시 잠그기 5ms |
| 저장 크기 | – | 건당 +35바이트 | 거의 그대로 |
| 메모리 | 41MB | 43MB(이름 재공유) / 50MB(재공유 없음) | 같음 |

- 건별을 고른 이유: 저장·수정·삭제·복구하기 흐름이 지금 그대로이고 두 곳(줄·덩어리)을 맞출 필요가 없어 단순하다. 연 6.7만 건 규모면 첫 진입이 약 0.7초 늘어나는 정도(비례 환산).

## 6. 한계 (설명서·PRD에 명시)
- 로그인한 뒤 화면을 보는 사람은 막지 못한다 → 5분 자동 잠금으로 보완.
- 평문 칸으로 헌금 건수·날짜 분포 같은 형태는 드러난다(누구의 얼마인지는 알 수 없음).
- 설치본은 개발자 도구가 꺼져 있다(이미 반영). 개발 실행(`npm run dev:app`)은 열린다.

## 7. 작업 순서 (커밋 단위)
1. main 인증(`electron/auth.cjs`, IPC) + 로그인 화면
2. 데이터 열쇠 + 저장소 층 건별 암호화 + 첫 암호화 이전 (**승인 후**)
3. 관리자 탭: 계정·비밀번호 변경·실패 기록·전체 초기화 이동·5분 자동 잠금
4. 연도 잠금 + 헌금 일괄 삭제
5. 문서: `PRD.md`, `ARCHITECTURE.md`, `docs/CODE_MAP.md`, 설명서 `helpContent.ts`(관리자 절, 복구 키 보관, 전체 초기화 위치)

## 8. 확인 방법
- 단위 테스트: `rules.ts`(이메일·비밀번호·한글), `electron/auth.cjs`(해시 검증·3회/10분·3명 제한·복구 키 1회용·열쇠 다시 잠그기), 저장소 암호화 왕복(평문 칸 유지·색인 조회 동작), 첫 이전 중단 후 이어하기, `deletePeriod` 건별 이력, `assertYearsUnlocked`.
- `npm test`, `npm run build`, `npm run smoke`: 스모크는 임시 데이터 폴더에서 phrase → 관리자 생성 → 로그인 IPC를 거친 뒤 기존 검사, 틀린 비밀번호 4회 시 종료·재실행 시 locked, 저장소 파일에 이름·금액이 평문으로 없는지 확인 추가.
- `npm run dev:app`: 첫 실행 흐름, 복구 키 저장·인쇄, 찾기, 자동 잠금(시험 때만 `STEWARD_TEST_IDLE_MS`로 단축, 포장본에서는 무시), 시연 데이터 20만 건으로 보고서 첫 진입 시간 재확인. 브라우저 모드는 그대로인지 확인.
